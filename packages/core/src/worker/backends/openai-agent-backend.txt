架构评价（优点 / 风险点）

优点：职责分层清晰（对话→规划→执行→会话治理），WorkerBackend 抽象做得早且统一，方便逐步引入“官方 SDK 后端”而不推翻 Orchestrator/Tools。
优点：SessionFileManager 的“可观察/可恢复/可审计”是你们和很多单体 CLI 拉开差距的核心（尤其适合多 worker 并发与人类介入）。
风险点：Generic backend 代码体量大且耦合多能力（上下文工程、Skills、Memory、协作、审批、并行工具队列等都在一个类里，见 packages/core/src/worker/backends/generic-agent-backend.ts (line 766)），未来加更多后端会反复做“工具适配/审批适配/消息映射”。
风险点：审批在后端等待会阻塞 generator，导致 CLI 现在靠文件侧通道兜底（packages/core/bin/tachikoma.ts (line 133)）；如果再引入新 backend，建议把“审批请求事件→统一等待/恢复”抽成通用组件，避免每个 backend 各写一套。
风险点：后端选择目前偏“隐式策略”（provider + useAgentSDK），扩展到更多可选 backend 时建议引入显式 backend 字段，否则 factory 会越来越难维护。
对标 Codex / Claude Code / Gemini CLI（架构层面）

业界这三类 CLI 通常是“单 agent + 工具执行循环 + 强交互 UX（diff/权限/恢复）”；你们走的是“Orchestrator-Workers + 会话文件协议 + 工具/上下文/记忆平台化”，更偏“agent runtime 平台”而不只是 CLI。
你们的差异化点：多 worker 协作、可审计文件协议、MCP 体系、上下文工程与 Skills/Memory/协作可组合；短板更可能在产品化交互（权限/审批的前台呈现）、默认策略调参、以及后端生态（官方 SDK 能力对齐）。
OpenAI Agents SDK（openai-agents-js）对你们有没有用

有用，但最合理的位置是“Worker 执行层可选后端”，而不是替换 Orchestrator：你们的 System 2 规划/分工/审计已经成体系，引入它更像获得一个“官方维护的 System 1 工具调用运行时”。
它能带来的增量主要是：标准化流事件（tool_called/tool_output/tool_approval_requested 等）、可恢复的 RunState、内建的 tool approval 机制、以及 OpenAI tracing exporter（更接近 Codex 一类运行时的形态）。
风险与成本：新增依赖与 API 迭代成本；默认偏 OpenAI（Responses vs Chat Completions）可能影响 OpenRouter 兼容；你们 Generic backend 里的上下文工程/并行工具/skills/memory 能力要么迁移、要么接受“新后端先不对齐”的质量落差。
