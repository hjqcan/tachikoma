第 1 章：提示链（Prompt Chaining）

是什么：把一个复杂任务拆成一串小步骤，每一步用一个专门的 prompt 解决一个子问题；上一步输出作为下一步的输入，形成“管道 / 流水线”。

解决什么问题：• 单条“大提示词”容易：• 上下文太长 → 超窗• 早期错误被放大• 模型认知负担太重 → 幻觉多• 多子任务混在一次调用里，某些子任务容易做得很差（例如能总结得不错，但邮件写得很烂）。

核心机制：• 明确拆分任务：分析 → 结构化 → 生成 → 校对 …
• 每一步只做一件事，并且 prompt 尽量短、清晰、专注。• 中间结果可以是自然语言、JSON、计划、代码片段等，都可以传给下一步。• 可以组合：• 顺序链（固定流程）• 有分支或循环的链（中间有条件判断）

对实现 agent 的启发：• 在代码中显式建模“步骤”：不要指望一个 llm_call 干完所有活。• 中间结构最好是 结构化数据（JSON），方便后续步骤消费。• 每一步里还可以继续用工具 /
RAG / 代码执行 —— 提示链是“总框架”。

第 2 章：路由（Routing）

是什么：给 agent 加上“条件分支与选择能力”，根据 当前输入 / 环境状态 / 上一步结果，动态决定要走哪条子流程、用哪个子 agent
/ 工具。

解决什么问题：• 提示链是固定顺序，但现实任务往往要：• 简单问题走快速通道• 复杂问题走详细流程• 不同类型任务走不同专家 / 工具• 没有路由的系统，只能“所有请求都走同一条链”，既慢又不准。

核心机制：• 先有一个 “Router
Agent”：• 识别意图（如：查订单、改地址、退款、技术问题…）• 决定调用哪个：• 专用子 agent
• 一段提示链• 一组工具• 可以实现为：• 一个专门的分类器 / LLM router • 一个带规则的混合策略（if +
LLM）• 支持：• 回退策略（没信心时走默认流程）• 级联路由（先粗分 → 再细分）

对实现 agent 的启发：• 在框架中预留 Router 角色，统一负责：• 任务类型识别• 路线 / 子 agent 选择• 所有子 agent、子流程用统一的“注册表”，便于 router 查询与扩展。

第 3 章：并行化（Parallelization）

是什么：把 互相独立 的子任务并行执行，例如多次 LLM 调用、多工具调用、多子 agent 同时跑，以缩短整体用时。

解决什么问题：• 顺序执行时，整体延迟 = 所有步骤延迟之和。• 很多任务其实可以：• 同时搜索多个来源• 同时分析多个文件• 同时给多个模块写代码

核心机制：• 识别工作流中哪些步骤 没有依赖关系，可以并发：• 并行：搜索 A、搜索 B
• 并行：总结 A、总结 B
• 顺序：最后整合总结• 需要一个调度层：• 负责编排并发调用、收集结果、处理异常（超时、单个失败等）。• 注意：• 并行任务越多，资源占用越大，要和成本 / 限流平衡。• 最后聚合步骤一般是顺序的，需要等待所有并发结果返回。

对实现 agent 的启发：• 在执行层加入统一并行执行器（如基于 Promise/Task/线程池）。• 接口上允许：•
executeInParallel([Task1, Task2, ...]) • 日后可结合资源感知模式，根据预算和延迟动态控制并发度。

第 4 章：反思（Reflection）

是什么：让 agent 在做完一轮之后，主动检查自己的输出 / 思路 / 行为，找问题、提改进建议，再进行修正或重做，是一种“自我评审 + 迭代”的模式。

解决什么问题：• 一次性输出的错误和不完善难以避免：• 逻辑漏洞、事实错误• 忽略约束条件• 风格、格式问题• 希望在不中断自动化的前提下，提高质量。

核心机制：

常见结构是两步 / 三步循环：1. 初稿执行：主 agent 按正常流程生成结果。2. 反思评审：• 同一个模型或另一个“评论员 agent”：• 按标准（正确性、完整性、风格、限制条件…）审查输出• 产出“批注 / 问题清单 / 改进建议” 3. 修正重写（可选多轮）：• 把批注作为新提示的一部分，让主 agent 生成改进版。

典型模式：• Self-critique（自我点评）• Red Team 评估（安全 / 合规评审）• Multi-round
refinement（多轮迭代）

对实现 agent 的启发：• 把“评审”当成一个独立阶段，而不是顺手一问。• 设计统一的“反思 prompt 模板”：让模型从结构化维度去点评，而不是随便讲几句。• 对代码、长文档、规划类任务，最好默认加一轮反思。

第 5 章：工具使用（Tool Use / Function Calling）

是什么：让 LLM/agent 通过函数调用机制，去调用外部 API / DB
/ 文件系统 / 代码执行环境等，实现“能查、能算、能操作”的能力。

解决什么问题：• 纯 LLM：• 无法实时查询• 算术和结构化操作不可靠• 无法真正改变外部世界• 通过工具，agent 才能成为“可以执行行动”的系统。

核心机制：

典型流程：1. 工具定义：每个工具包含：• name • description • input schema（参数结构）• output
schema 2. 选择工具：LLM 通过 system
prompt 或内驱逻辑，判断：• 是否需要工具？• 需要哪一个？3. 生成调用：按 JSON
/ 函数调用格式输出参数。4. 执行工具（在宿主程序）：调用真实 API
→ 得到结果。5. 结果回注入 LLM：作为新的上下文，继续推理或生成。

对实现 agent 的启发：• 要设计“工具注册中心”：统一管理所有 tool 的 metadata。• 和路由、规划结合：• 规划决定“什么时候需要工具”
• 路由决定“用哪个工具” • 工具调用一定要带严格 schema 校验，避免脏输入把系统搞挂。

第 6 章：规划（Planning）

是什么：把 agent 当成一个“能做计划的专家”：给它一个 目标 + 约束，它要先产出一份可执行的计划，然后再按计划行动，并在过程中动态更新计划。

解决什么问题：• 复杂任务往往需要：• 明确步骤顺序• 处理依赖关系• 考虑资源 / 时间 / 风险• 如果 agent 只是一边想一边做，很容易迷路或反复。

核心机制：• 输入：目标（Goal）+ 上下文 + 约束（预算、时间、风险偏好…）• 输出一个结构化计划，例如：• 任务列表（Task1…TaskN）• 每个任务包含：• 描述• 依赖的任务• 建议工具 / 子 agent
• 完成标志• 执行过程中：• 获取新信息（工具结果、外部事件）• 对计划做：• 调整顺序• 拆分 / 合并任务• 标记完成 / 失败

对实现 agent 的启发：• 可以把 Planner 做成一个独立组件：• plan()：生成计划•
replan()：基于当前进度重构计划• 喂给 coding agent 时，应要求它：• 先吐出 plan 的 JSON
• 再按 plan 一步步执行（而不是直接写代码/结果）

第 7 章：多智能体协作（Multi-Agent Collaboration）

是什么：用“团队”的思路设计系统：把大问题拆给多个 专长不同的 agent，再用协调机制把它们的结果整合起来。

解决什么问题：• 单一“大 agent”：• 指令越来越复杂• 提示词越来越长• 既要会写文案，又要会查数据，还要会写代码 → 很容易混乱• 多 agent：• 每个只负责一类任务，提示简单，容易优化和调试。

核心机制：• 角色划分：• 例如：调度/PM agent、研究 agent、代码 agent、Reviewer agent…
• 通信机制：• 统一消息格式（包含：from、to、任务、结果、状态）• 可能通过“共享黑板 / 中央存储”协作• 协调方式：• 集中式：一个 orchestrator 决定谁干啥• 分布式：多个 agent 互相发任务（更复杂）

对实现 agent 的启发：• 不要一上来做“万能大脑”，从简单的双/三 agent 协作开始：• PM agent 拆任务•
Worker agent 执行• Reviewer agent 审核• 把消息传递、状态存储设计成通用层，以后可以挂更多 agent。

第 8 章：记忆管理（Memory Management）

是什么：系统化管理 agent 的“记忆”——包括：• 短期记忆（context
window 内的临时信息）• 长期记忆（持久存储的经验 / 文档 / 用户偏好）

解决什么问题：• 没记忆的 agent：• 每次对话都从零开始• 不知道之前发生了什么• 做不了长期任务和个性化• 记忆乱七八糟的 agent：•
token 爆炸• 取错信息• 上下文污染严重

核心机制：• 短期记忆：• 类似“工作记忆”，就是当前对话/任务的关键信息• 受上下文长度限制，需要：• 截断策略• 摘要策略• 长期记忆：• 存在外部存储（DB
/ 向量库）• 包含：文档、历史任务、用户偏好、经验总结…
• 通过检索（关键词 + 向量）加载到短期记忆中• 记忆生命周期：• 写入（什么时候存？）• 更新（旧信息过期/修正）• 删除或归档

对实现 agent 的启发：• 定义好记忆类型：会话级 / 用户级 / 全局知识级。• 必须实现：•
remember()：写入长期记忆•
recall()：按当前任务检索记忆• 要结合“上下文工程”，避免把所有记忆一股脑塞进 prompt。

第 9 章：学习与适应（Learning and Adaptation）

是什么：让 agent 根据经验改变自己——不只是记住信息，而是：• 调整策略• 改变行为偏好• 优化 prompt
/ 工具使用方式使得它随着时间变得更“聪明”。

解决什么问题：• 传统 agent 行为固定：• 永远按照预设流程和 prompt 走• 学习型 agent：• 可以利用历史任务结果不断改良策略• 适应新场景、新需求

核心机制（章节里提到的主要方向）：• 强化学习（RL）：通过“行动 → 奖励/惩罚”来学策略，很适合：• 控制机器人• 游戏/仿真环境中的长期决策• 监督学习 / 模仿学习：通过记录“人类是如何做”的示例，训练出类似行为。• 在线学习 / 经验回放：持续从运行日志中抽取数据，更新策略或辅助模型。• 元学习 &
prompt/策略优化：• 学习“如何更好地提问 / 规划” • 把“好的流程 / prompt”自动归纳为可复用模板

对实现 agent 的启发：• 即便不做复杂 RL，也可以做“轻量学习”：• 记录 task
→ 结果 → 总结 → 下次相似任务时优先参考• 统计哪种工具/提示效果好，自动提升权重• 把“经验总结”存进长期记忆，并在相似任务中自动检索。

第 10 章：模型上下文协议（Model Context Protocol, MCP）

是什么：MCP 是一种专门为 LLM/agent 设计的标准协议，用来统一：• 怎么暴露外部资源（数据源、工具等）• 怎么让模型去发现、调用这些资源

可以理解为：LLM 与外部世界之间的通用适配层。

解决什么问题：• 没有统一协议的时候：• 每接一个新系统，都要定制接入方式• 工具、数据源、模型之间难以复用•
MCP 把：• 资源（Resources）• 工具（Tools）• 提示模板（Prompts）统一抽象并通过标准接口暴露给模型。

核心机制：• 基于 Client-Server 架构：• MCP
Server 暴露：• 可访问的数据源（如文件、DB）• 可调用的工具（API、脚本等）• 可复用的 prompt 模板• MCP
Client（通常是 LLM 应用 / agent）：• 通过协议发现、列举、调用这些资源和工具。•
MCP 本质上定义的是“agentic interface 的契约”：• 并不强制你怎么实现具体 API
• 但约束了“描述和调用”的方式，使之可被 LLM 稳定理解和使用。

对实现 agent 的启发：• 如果你要做一个可插拔、多工具、多数据源的 agent 平台：• 很值得将工具/资源层抽象成类似 MCP 的接口。• 即便不用官方 MCP，也可以借鉴思想：• 工具 / 数据源都要有统一的元数据描述•
LLM 根据这些元数据自动决定怎么用资源• 宿主只负责实现具体逻辑

第 11 章：目标设定与监控（Goal Setting & Monitoring）

是什么：让 Agent 能够：1. 明确目标（Goal）2. 定义成功标准（Success
Criteria）3. 持续监控执行进度（Monitoring）4. 在偏离目标时主动调整策略（Adaptation）

解决什么问题：• 没目标 →
Agent 行为混乱• 目标模糊 → 输出偏题、浪费资源• 缺监控 → 出现错误却继续执行• 缺成功标准 → 无法判断任务何时完成

核心机制：• 将用户模糊需求 → 转换为结构化目标：{ "goal": "Rewrite the report", "constraints":
["tone: professional", "length: <2000 words"], "success_criteria": ["no grammar errors", "references
preserved"] } • 监控任务执行过程中关键状态• 若偏离目标 → 触发 replanning • 若接近完成 → 执行验证步骤

对 Coding
Agent 的启发：• 在写代码前先输出目标 JSON• 在执行子任务时持续验证：• 是否朝着目标推进？• 是否违反了约束？• 如偏离 → 自主调整• 最后产出一个 success
checklist 逐项对照

第 12 章：异常处理与恢复（Exception Handling & Recovery）

是什么：为 Agent 提供 健壮的容错机制，让任务在失败或环境问题发生时仍能继续运行。

解决什么问题：• API 崩溃• 工具返回异常格式• 网络错误• LLM 输出格式错误• 中途任务失败导致全流程崩溃

核心机制：• 包含主动 + 被动两类：• 被动恢复：• 失败重试• 回退执行（fallback）• 换工具 / 换策略• 部分执行回滚• 主动预防：• 参数校验• 输出 schema 检查• 超时机制• 工具沙箱

对 Coding Agent 的启发：• 给每一步工具调用外层加：• try → catch → retry →
fallback• 对 LLM 输出进行严格 JSON schema 校验• 若遇到错误：• 自动修复 prompt
• 自动修复格式• 自动 replan 这是 Coding Agent 走向可生产化的关键能力。

第 13 章：人类在环（Human-in-the-Loop, HITL）

是什么：允许 Agent 在关键步骤主动请求人类确认或输入。

解决什么问题：• 高风险错误（医疗、金融、部署、删除数据）• 创意任务需要人工品味• 歧义输入必须让人澄清

核心机制：•
HITL 触发点：1. 不确定性高时（模型置信度低）2. 多方案都有风险时 3. 用户意图模糊时 4. 输出行动不可逆（如删除仓库）•
HITL 交互格式：• “我有 A、B、C 三个方案，你要哪个？” • “这个结果是否符合你的预期？” •
“是否继续执行下一阶段？”

对 CodingAgent 的启发：• 在关键情况下暂停执行• 清晰列出可选项与分析• 等待用户确认后再继续• 若无人响应，保持任务安全暂停

第 14 章：知识检索（Knowledge Retrieval / RAG）

是什么：在生成答案前，Agent 从知识库检索相关内容加入上下文。

解决什么问题：•
LLM 记忆有限• 模型知识过时• 领域内容（文档、API、代码库）需要实时查找• 纯模型回答不可靠

核心机制：• RAG 流程：1. 根据任务自动生成查询（query-generation）2. 检索知识（embedding /
keyword）3. 对检索结果做摘要 + 切片 4. 将结果注入 LLM

对 Coding Agent 的启发：• 在写代码前自动检索：• 项目文件•
API 文档• 依赖库定义• 检索结果必须经过上下文工程处理：• 只保留相关部分• 控制在 token 限制内

第 15 章：智能体间通信（Inter-Agent Communication）

第 16 章：资源感知优化（Resource-Aware Optimization）

是什么：让 Agent 在执行中随时考虑成本、延迟、上下文大小等资源限制。

解决什么问题：• LLM token 超限• 调用太贵的模型造成成本浪费• 并发任务占用资源过多• 响应速度太慢

核心机制：• 系统会动态选择：• 哪个模型（cheap vs powerful）• 哪种策略（fast vs
accurate）• 哪个上下文（全文 vs 摘要）• 哪种执行路径（并行 vs 串行）

对 Coding
Agent 的启发：• 判断当前任务是否需要大模型• 遇到简单任务用便宜模型• 避免加载大型文件进入上下文• 压缩代码/文档，避免 token 爆炸• 提供执行成本估算

第 17 章：推理技术（Reasoning Techniques）

是什么：引入结构化、多步骤、可控的推理策略，如：• Chain-of-Thought • Tree-of-Thought • Debate •
Deliberate • Program-of-Thought

解决什么问题：• 一步输出不可靠• 多跳推理失败• 对复杂逻辑问题表现不稳定

核心机制：• 推理模式能：• 显式展示思考过程• 让模型在多个候选答案中选择最优• 生成推理路径用于可解释性• 在必要时调用工具进行逻辑检验

对 Coding Agent 的启发：• 使用 multi-step
reasoning 分析代码错误• 对复杂重构需求进行 Tree-of-Thought• 对不同解决方案进行比对• 允许 reviewer
agent 检查推理过程

第 21 章：探索与发现（Exploration and Discovery）

是什么：探索与发现模式让 Agent 不仅限于完成既定任务（exploitation），还具备主动：• 寻找未知信息• 打开新的解空间• 提出新假设• 从失败中更新认知• 不断扩展能力。这使 Agent 不再只是“执行指令的机器”，而是能主动寻找机会、探索未知、持续学习成长的系统。

解决什么问题：• 当任务空间未知或不完整时，固定策略会失败（如研究任务、未知 bug、创意设计）。• 严格按照计划执行的 agent 容易陷入局部最优。• 需要 agent 在“没有明确答案”的领域提出新方向。

核心机制：• 多假设生成（Multi-Hypothesis
Generation）：Agent 主动产出多个假设、推测、解决方案或研究方向，然后基于这些做展开。• 实验驱动（Experimentation
Loop）：提出假设 → 生成实验 → 执行实验 → 观察结果 → 更新知识 → 下一轮探索。• 搜索解空间（Search in
Concept Space）：主动搜索替代方案、改写 prompt、生成不同架构等。• 容忍不确定性（Uncertainty
Tolerance）：在不完整信息下推断，明确不确定性等级，关键点请求人类确认。• 主动思维（Proactive
Discovery）：识别缺失信息、潜在提升点、边角场景等。

对 Coding
Agent 的启发：• 主动提出多种可行方案：不再只是执行，而是思考可能性。• 自动生成实验脚本 / 测试用例：针对不确定问题，生成 A/B 实验、Perf 脚本、测试用例。• 在遇到不确定代码时主动探索推断路径：阅读文件、RAG 检索、猜测影响。• 主动告诉用户“这里还有潜在问题/提升点”：如代码优化、架构风险、缺测试等。• 给出新的探索方向：建议新的架构模式或技术方案。• 探索更好的 prompt
/ 工具使用策略：自我优化。• 自动在必要时请求用户确认：让探索可控。

结构化探索模板：{ "exploration": { "hypotheses": [...], "experiments": [...],
"alternative_solutions": [...], "risks": [...], "unknowns": [...], "recommendations": [...] } }
